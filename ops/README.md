## Secrets and database TLS

Run `node ops/prepare-secrets.mjs` locally after verifying the three existing ignored production source files are still authoritative. It creates a new private ignored directory, never overwrites a prior one, preserves the actual OAuth client and both existing action/Calendar encryption keys, and creates separate random PostgreSQL roles/passwords and a new backup key. It prints paths only. The pull of Vercel sensitive variables contains placeholders, and MUST NOT replace these real local keys.

Install the generated files on the host under `/srv/studentvalue/secrets`, owned by root, directory 0700/files 0600. Compose reads protected env files; they never enter an image or Git. Keep another private copy of the backup key and application encryption keys outside this VPS. `app.env` must not contain Vercel/test/development overrides or Neon URLs. `migration.env` belongs only to the one-shot migration job, not the web app. PostgreSQL has no published port. Its separate internal network accepts TLS/SCRAM only, with separate app and migration roles. The web app validates the CA and hostname and refuses an owner/superuser URL.

Next 15's private server-action manifest can contain its build encryption key. Treat application images and standalone server artifacts as private secret-bearing artifacts: build/store them on the protected host, never push them to a public registry or serve the server directory as static files. The runtime still requires the same persistent key. The production build removes Next's generated dotenv copies from standalone output; it never removes the original local env files. Docker's allowlist also excludes env files from the input context.

Create a private local CA outside the database mount and a server certificate with `subjectAltName=DNS:db`, signed by that CA. Mount only `ca.crt`, `server.crt` and `server.key` in `/srv/studentvalue/tls/db`. The key must be owned by PostgreSQL container UID 999, mode 0600; certificates can be 0644. Do not accept invalid certificates or disable TLS to get the stack running. Set certificate-expiry monitoring and renewal before cutover; public HTTPS certificates are renewed automatically by Caddy.

## Release and migration sequence

1. Build only a checked clean commit using `sh ops/build-images.sh`. The action key goes through BuildKit's secret mount, never Docker ARGs. Compilation uses a deliberately unreachable build-only DB URL and never migrates/seeds. Runtime images contain traced standalone output and public assets, not tests, secrets, private course files or the local corpus. Docker builds require a Docker daemon; this Mac's current environment has none, so actual image/TLS startup validation is pending the target host.
2. Set immutable `APP_IMAGE=studentvalue:<commit>` and `MIGRATION_IMAGE=studentvalue-migration:<commit>` plus `ACME_EMAIL` in the protected `release.env`. Use `docker compose --env-file /srv/studentvalue/secrets/release.env -f ops/compose.yml …` for all stack commands. Do not use `latest` or copy the working development database.
3. Start **only** `db`. Check TLS by certificate-verified connections and prove the application role cannot create tables or read/write `_prisma_migrations`. Before migration, exercise all migrations and restore rehearsal in a separate disposable target database. Do not mistake the encrypted JSON safety snapshot for a PostgreSQL dump or a completed restore test.
4. Take a real consistent source `pg_dump --format=custom --no-owner --no-acl` from the existing direct Neon source, encrypted while streaming. Check its authenticated digest and archive catalog. Rehearse restoration on a separate database/server; compare every application table's counts and content digests, file-byte hashes, keys, memberships, sessions, progress, source references and Calendar stable IDs. Source-side RLS/roles and migration ledger ownership need deliberate review, not a blindly executed role dump.
5. For the final cutover, stop writes and background jobs on the old deployment, drain in-flight work, and take the final dump. Verify the target is empty; restore under `studentvalue_migrate`, retain the original source and encrypted dump, and revoke app access to `_prisma_migrations`. Never use `--clean`, reset, drop, or overwrite a populated target. Run `compose run --rm migrate` for saved migrations and ledger privilege cleanup. No seeding.
6. Start the app. Check `/api/health/live`, DB readiness, public pages and auth rejection from the internal network. Before DNS changes prove canonical-host HTTPS routing against the VPS, Google callback configuration, a real ordinary-student/headman session, private download guards and actual Calendar readback. A new source-IP failure must be fixed before moving DNS.
7. Only after those checks update the owner's existing GNAME apex A record to the VPS IPv4; remove an obsolete AAAA if necessary. Keep the old deployment in maintenance until DNS caches drain. The canonical domain and Google callback stay unchanged. If target verification fails, restore DNS and the old writable deployment before accepting writes on the new one. After new writes begin, rollback requires reconciling those writes; a stale reverse switch is unsafe.

## Jobs, backups and remaining acceptance checks

Install the two `studentvalue-*.service`/`.timer` pairs in systemd and point `/srv/studentvalue/current` to the checked release. Calendar runs every five minutes using the existing authenticated cron endpoint and durable queue; failures do not mark work as synced. Keep the old Vercel cron inactive after cutover, and verify the timer's real execution, not just its presence.

`ops/backup.mjs` streams `pg_dump` to AES-256-GCM (header `SVPG1` + 12-byte IV as AAD; ciphertext + 16-byte tag), authenticates and compares the plaintext digest in memory, then renames the exclusive 0600 partial file. It does not write a plaintext archive, delete older backups, or call an unconfigured external service. A failed/partial file is never successful. The daily timer alone is **local backup only**. Before retiring Neon, configure an independently accessible off-server destination, exercise recovery on a separate database, monitor backup age/disk space/service health, and retain the source until recovery has been proven. Caddy logs intentionally omit an access log that would retain OAuth callback query strings.

Moving the server does not turn browser login into delegated university API access. `/university` currently offers local user-controlled copies of recordbook/study-plan tables and explicit external service links. Corporate mail, Moodle/OpenEdu background synchronization, internal directory querying and messenger operations still need supported per-user authorization, credential isolation and transport tests. No university passwords, cookies, personal grades or contacts have been moved to Vercel/Neon as part of this work.
