## ADR-001: Выбор базового стека (Next.js 15 App Router + TypeScript + Tailwind CSS)
*Статус:* Принято.  
*Контекст:* Продукт создается для регулярного повседневного использования студентами с ноутбуков и смартфонов. Главные требования: мгновенная скорость открытия дашборда («Что мне делать прямо сейчас?»), низкий overhead на стороне клиента, типобезопасность по всей глубине приложения и чистая компонентная база.  
*Решение:* Next.js 15+ с App Router и React Server Components (RSC), TypeScript (`strict: true`), Tailwind CSS с кастомной дизайн-системой на CSS-переменных для мгновенного переключения Dark/Light режимов.

## ADR-002: Выбор СУБД и ORM (PostgreSQL + Prisma)
*Статус:* Принято.  
*Контекст:* Учебный процесс требует реляционной целостности: каскадные удаления заданий, зависимостей, ролей, прав и истории прогресса. Одновременно необходима поддержка неструктурированных данных: структурированные условия допуска (`gradingMetadata`), динамические требования и контекст AI-предложений.  
*Решение:* PostgreSQL 16+ в связке с Prisma ORM. Для полей с динамической схемой использовать нативный тип `JSONB`.

## ADR-004: Разделение CourseDefinition и CourseOffering (Динамический каталог)
*Статус:* Принято.  
*Контекст:* Учебная группа 5130901/40102 — первая, но смежная группа 5130901/40101 имеет похожий учебный план, тех же преподавателей и общие методички, но разные дедлайны, аудитории и дни пар. Никакие списки предметов не должны быть захардкожены в коде.  
*Решение:*  
1. `CourseDefinition` — дисциплина в принципе (наименование, код, описание). Включает все дисциплины семестра (в том числе «Образовательный форсайт» и «Системный анализ и принятие решений»).  
2. `CourseOffering` — проведение курса в конкретном семестре для одной или нескольких групп.  
3. UI и навигация получают список всех дисциплин исключительно динамически через запрос к активным `CourseOffering` в БД.

## ADR-005: Гранулярная ролевая модель (Telegram-like Permission RBAC)
*Статус:* Принято.  
*Контекст:* Жесткая схема `student / admin` не удовлетворяет потребностям студенческой группы: староста должен иметь возможность делегировать наполнение конкретного предмета (Course Manager) без передачи полного контроля над группой.  
*Решение:* Динамическая permission-based модель: набор атомарных прав (`manage_tasks`, `manage_deadlines`, `manage_materials`, `verify_progress`, `manage_course:<offeringId>`). Любая мутация проверяется на сервере.

## ADR-009: Конкретный механизм аутентификации и валидация Telegram (2026)

### Контекст
Требуется конкретное, надежное архитектурное решение аутентификации вместо расплывчатых формулировок. Необходима поддержка входа через Google и Telegram, сохранение структуры `User -> AuthIdentity[]` и категорический запрет автоматического объединения профилей по display name или email.

### Решение
1. **Архитектура сессий:**
   - Серверная сессия на базе таблицы `Session` в БД с криптографически стойким идентификатором сессии (`token = crypto.randomBytes(32).toString('hex')`).
   - Идентификатор передается в защищенной HTTP-only cookie с атрибутами `Secure`, `SameSite=Lax`, `Path=/`, префиксом `__Host-session` в production.
2. **Провайдер Google:**
   - Стандартный OAuth2 Authorization Code Flow с параметрами `openid email profile`.
   - Проверка `id_token` через публичные ключи Google JWKS.
3. **Провайдер Telegram (Стандарты 2026 года):**
   - **Сценарий 1 (Web): Telegram Login Widget.** При авторизации Telegram виджет передает объект данных (`id`, `first_name`, `last_name`, `username`, `photo_url`, `auth_date`, `hash`). Бэкенд валидирует подпись:
     $$\text{secret\_key} = \text{SHA-256}(\text{BOT\_TOKEN})$$
     $$\text{check\_hash} = \text{HMAC-SHA-256}(\text{data\_check\_string}, \text{secret\_key})$$
     Если `check_hash !== hash` или `auth_date` старше 24 часов — запрос отклоняется.
   - **Сценарий 2 (Telegram WebApp / Mini App):** Валидация `Telegram.WebApp.initData` по алгоритму HMAC-SHA-256 с ключом `HMAC-SHA-256("WebAppData", BOT_TOKEN)`.
4. **Инвариант множественной идентичности:**
   - Один пользователь `User` может иметь несколько связанных `AuthIdentity` (Google, Telegram).
   - Связывание нового провайдера возможно **только** из активной сессии аутентифицированного пользователя (Account Linking Flow).
   - **Строгий запрет:** Автоматическое связывание по email или имени пользователя запрещено.

## ADR-010: Разделение Enrollment и GroupMembership & Инварианты связывания

### Контекст
Необходимо четко развести академический список группы от учетных записей зарегистрированных пользователей приложения, исключив двойные источники истины и утечку персональных данных.

### Решение
1. `Enrollment` — запись в университетском списке группы:
   - Содержит реальное ФИО (`fullName`), подгруппу (`subgroup`), номер зачетки/студбилета.
   - Создается старостой заранее (ручной ввод или CSV-импорт).
   - Статусы: `PENDING_CLAIM` $\to$ `CLAIMED` $\to$ `VERIFIED` $\to$ `ARCHIVED`.
2. `GroupMember` — участие зарегистрированного `User` в пространстве группы приложения:
   - Связывает `User.id` и `StudyGroup.id`.
   - Хранит флаг владельца (`isOwner`), дату вступления и ссылки на назначенные роли.
3. **Инвариант подтвержденной связи User $\leftrightarrow$ Enrollment:**
   - Поле `Enrollment.userId` является внешним ключом на `User.id` с уникальным ограничением `UNIQUE(groupId, userId)`.
   - Один физический пользователь не может быть связан более чем с одной записью в списке одной группы.
   - Связывание осуществляется либо по одноразовому криптографическому токену `claimToken`, выданному старостой, либо прямым подтверждением старосты (`verify_enrollment`).
4. **Приватность:**
   - Публично одногруппники видят только профиль `User` (`nickname`, `avatarUrl`).
   - Связка `User` $\to$ `Enrollment` (реальное ФИО) доступна строго администраторам с правом `view_private_member_identity`.

## ADR-011: Вынесение Deadline и ExternalCalendarEvent в отдельные сущности

### Контекст
Хранение `dueAt` и `externalCalendarEventId` непосредственно в `Task` делает невозможным поддержку нескольких сроков (рекомендуемый vs жесткий дедлайн), переносов сроков со сбережением истории, дедлайнов по подгруппам и изоляции сбоев календаря.

### Решение
1. `Deadline` выделяется в самостоятельную первоклассную сущность:
   - `taskId` (FK $\to$ `Task`);
   - `title` (опциональное наименование: «Мягкий дедлайн», «Защита на паре», «Окончательный срок»);
   - `type` (`HARD`, `SOFT`);
   - `date` (TimestampTZ);
   - `isTimeStrict` (Boolean — учет точного времени или всей даты);
   - `status` (`ACTIVE`, `POSTPONED`, `CANCELLED`);
   - `originalDeadlineId` (nullable FK на себя для сохранения истории переноса);
   - `sourceReferenceId` (FK $\to$ `SourceReference`).
2. `ExternalCalendarEvent` выделяется в отдельную сущность интеграции:
   - `deadlineId` (FK $\to$ `Deadline`);
   - `calendarId`, `externalEventId`;
   - `syncStatus` (`SYNCED`, `PENDING_UPDATE`, `PENDING_DELETE`, `FAILED`).
3. Задание `Task` ссылается на свои дедлайны через отношение 1-to-many.

## ADR-012: Полноценная модель источников данных (Source & SourceReference)

### Контекст
Для обеспечения принципа *FACTS != PRODUCT ASSUMPTIONS* и подготовки к будущей AI-инжестии (извлечение заданий из транскриптов и ответов на вопросы с точным цитированием первоисточника) недостаточно простого enum.

### Решение
Спроектировать двухуровневую модель источников:
1. `Source` — физический или логический источник информации:
   - `type` (`OFFICIAL_DOCUMENT`, `TEACHER_STATEMENT`, `HEADMAN_RECORD`, `CLASS_SESSION`, `TRANSCRIPT_SEGMENT`, `STUDENT_PERSONAL`);
   - `title`, `url`, `documentMetadata` (JSONB: страницы, реквизиты);
   - Внешние ключи на `Teacher`, `ClassSession`, `Transcript`.
2. `SourceReference` — конкретная ссылка/цитата, подтверждающая факт:
   - `sourceId` (FK $\to$ `Source`);
   - `entityType` (`TASK`, `DEADLINE`, `ANNOUNCEMENT`, `COURSE_TEACHER`, `REQUIREMENT`);
   - `entityId` (UUID целевой сущности);
   - `quoteText` (точный текстовый фрагмент/цитата);
   - `confidence` (`CONFIRMED`, `INFERRED`, `DISPUTED`);
   - `offsetStart`, `offsetEnd` (символьные смещения или миллисекунды в аудио).
3. Сущности `Task`, `Deadline`, `Announcement` и связь `CourseTeacher` связываются с `SourceReference`.

## ADR-013: Разделение доменного AuditLog и Security/Access Logging

### Контекст
Запись каждого отказа доступа (403 Forbidden) или попыток зондирования в доменный журнал засоряет историю аудита бизнес-данных и создает риски DoS базы данных.

### Решение
1. `AuditLog` — строго доменный аудит значимых изменений данных и полномочий:
   - Создание/удаление заданий, перенос дедлайнов, изменение ролей, привязка `Enrollment`, публикация объявлений.
2. `SecurityAccessLog` — отдельный системный лог:
   - 401 Unauthorized, 403 Forbidden, rate limit violations, подозрительные попытки авторизации.
   - Хранится отдельно (или направляется в стандартный structured log stream / stdout) с автоматической ротацией.

## ADR-014: Индивидуальные варианты заданий (TaskVariant) и аудитория (TaskAudience)

### Контекст
В учебном процессе СПбПУ (ОТУ, Компиляторы, САПР, FPGA) задания выдаются по индивидуальным вариантам. Создавать отдельный `Task` на каждого студента недопустимо. Также некоторые задания выдаются только отдельной подгруппе или группе.

### Решение
1. `TaskVariant` — сущность варианта задания:
   - `taskId` (FK $\to$ `Task`);
   - `variantNumber` (String/Int, например «Вар. 4», «12»);
   - `title`, `spec` (JSONB / Text с индивидуальными параметрами: матрица ОУ, входной язык, схема);
   - `sourceUrl` (ссылка на персональный файл варианта).
2. `VariantAssignment` — назначение варианта конкретному студенту:
   - `taskVariantId` (FK $\to$ `TaskVariant`);
   - `enrollmentId` (FK $\to$ `Enrollment`);
   - `assignedBy` (`TEACHER_ROSTER`, `HEADMAN`, `SELF_PICK`).
3. `TaskAudience` — гибкая адресация задания:
   - `taskId` (FK $\to$ `Task`);
   - `targetType` (`ALL_COURSE`, `GROUP`, `SUBGROUP`, `INDIVIDUAL`);
   - `groupId`, `subgroupNumber`, `enrollmentId`.
   - В MVP по умолчанию задание создается для всей группы (`GROUP`).

## ADR-015: Модель доверия и верификации статусов сдачи (Trust Model for ACCEPTED)

### Контекст
Событие *«Студент сдал отчет / считает, что сдал»* и событие *«Преподаватель официально принял и защитил работу»* принципиально различаются. Студент не должен иметь возможности самостоятельно выставить себе статус официальной приемки (`ACCEPTED`).

### Решение
1. `Task.status` (состояние публикации задачи):
   - `DRAFT`, `PUBLISHED`, `ARCHIVED`, `CANCELLED`.
2. `StudentTaskProgress.status` (жизненный цикл прохождения студентом):
   - `NOT_STARTED` $\to$ `IN_PROGRESS` $\to$ `READY` $\to$ `SUBMITTED` $\to$ `ACCEPTED` / `NEEDS_FIX`.
3. **Разделение прав на установку статусов:**
   - Обычный студент может переключать свой статус только в диапазоне: `NOT_STARTED`, `IN_PROGRESS`, `READY`, `SUBMITTED`.
   - Статус `ACCEPTED` с отметкой `isVerified = true` может быть установлен **только**:
     a) Пользователем с правом `verify_progress` (староста / доверенный ассистент);
     b) Через официальный импорт ведомости преподавателя.
   - Если студент сам отмечает работу как «сдана/защищена», она переходит в статус `SUBMITTED` (Self-Reported) с пометкой «Ожидает верификации».

## ADR-016: Изоляция Dev Role Switcher

### Контекст
Для тестирования вертикального среза необходима возможность проверки сценариев от лица обычного студента и старосты. Однако отладочные переключатели ролей создают критическую уязвимость, если случайно попадают в production.

### Решение
1. Dev Role Switch доступен **исключительно** при условии:
   `process.env.NODE_ENV === 'development'`.
2. В production сборке Next.js код dev-компонента исключается (dead-code elimination), а серверные API переключения ролей возвращают `404 Not Found`.
3. Для тестов используются постоянные seed-аккаунты (`dev-owner` — Батукаев Расул и `dev-student`).
4. Авторизация на бэкенде в любом режиме исполняет **реальные проверки прав** через сессию и базу данных.
