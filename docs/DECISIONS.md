## ADR-001: Выбор базового стека (Next.js 15 App Router + TypeScript + Tailwind CSS)

### Контекст
Продукт создается для регулярного повседневного использования студентами с ноутбуков и смартфонов. Главные требования: мгновенная скорость открытия дашборда («Что мне делать прямо сейчас?»), низкий overhead на стороне клиента, типобезопасность по всей глубине приложения и чистая компонентная база.

### Решение
1. **Фреймворк:** Next.js 15+ с App Router и React Server Components (RSC). RSC позволяют агрегировать данные на сервере в один быстрый запрос к БД и отдавать браузеру готовый HTML/компоненты без лишнего клиентского JavaScript.
2. **Язык:** TypeScript в строгом режиме (`strict: true`).
3. **Стили:** Tailwind CSS с кастомной дизайн-системой на CSS-переменных для мгновенного переключения Dark/Light режимов.

### Последствия
- Высокая производительность и быстродействие при холодном старте.
- Отсутствие рассинхронизации типов между бэкендом и фронтендом.
- Нет привязки к тяжеловесным сторонним дизайн-библиотекам.

## ADR-002: Выбор СУБД и ORM (PostgreSQL + Prisma)

### Контекст
Учебный процесс требует реляционной целостности: каскадные удаления заданий, зависимостей, ролей, прав и истории прогресса. Одновременно необходима поддержка неструктурированных данных: структурированные условия допуска (`gradingMetadata`), динамические требования и контекст AI-предложений.

### Решение
Использовать **PostgreSQL** в качестве основной реляционной СУБД в связке с **Prisma ORM**. Для полей с динамической схемой использовать нативный тип `JSONB`.

### Последствия
- Полная транзакционность (ACID) для критичных операций смены статусов и начисления XP.
- Автоматическая генерация миграций и типобезопасный клиент для работы с данными.
- Возможность использования полнотекстового поиска PostgreSQL по материалам и объявлениям.

## ADR-003: Разделение User, AuthIdentity и Enrollment (Multi-Identity & Privacy)

### Контекст
Студент может входить в систему через Google или Telegram. При этом у одного физического студента должен быть строго один аккаунт. Нельзя допускать дубликатов или автоматического слияния профилей по строковому совпадению имени. Также старосте необходимо загрузить список группы до того, как студенты зарегистрируются.

### Решение
Разделить сущности на три независимых слоя:
1. `User` — внутренний неизменный профиль (id, nickname, avatar).
2. `AuthIdentity` — связь с внешним провайдером авторизации (`provider`, `providerUserId`).
3. `Enrollment` — запись в университетском списке группы (реальное ФИО, подгруппа), которая связывается с `User` через безопасный токен или подтверждение старостой.

### Последствия
- Поддержка множественных провайдеров входа для одного пользователя.
- Исключена утечка реальных ФИО — публично видны только никнеймы.
- Безопасное связывание аккаунтов только из активной сессии пользователя.

## ADR-004: Разделение CourseDefinition и CourseOffering

### Контекст
Учебная группа 5130901/40102 — первая, но смежная группа 5130901/40101 имеет похожий учебный план, тех же преподавателей и общие методички, но разные дедлайны, аудитории и дни пар. В будущем система должна легко масштабироваться на другие группы без дублирования описания дисциплин.

### Решение
Разделить предметную область на:
- `CourseDefinition` (дисциплина в принципе: наименование, код, общее описание);
- `CourseOffering` (проведение курса в конкретном семестре для одной или нескольких групп: дедлайны, преподаватели, требования к зачету).

### Последствия
- 40102 и 40101 могут использовать общие материалы дисциплины, сохраняя раздельные списки задач и дедлайнов.
- Чистая структура базы данных без жесткого хардкода группы 40102 в сущностях курсов.

## ADR-005: Гранулярная ролевая модель (Telegram-like Permission RBAC)

### Контекст
Жесткая схема `student / admin` не удовлетворяет потребностям студенческой группы: староста должен иметь возможность делегировать наполнение конкретного предмета (например, назначить ответственного за лабораторные по FPGA) без передачи полного контроля над группой.

### Решение
Реализовать динамическую permission-based модель авторизации:
- Набор атомарных прав (`manage_tasks`, `manage_deadlines`, `manage_materials`, `manage_course:<id>`);
- Роли в группе являются контейнерами прав;
- Любая административная операция на сервере проверяет наличие конкретного атомарного права.

### Последствия
- Староста (Owner) может гибко наделять одногруппников правами и отзывать их в любой момент.
- Полная защита на уровне сервера: скрытие кнопки в UI никогда не считается достаточной мерой безопасности.

## ADR-006: Идемпотентный движок геймификации (Event-Driven Idempotent XP)

### Контекст
Геймификация должна стимулировать учебу, но не превращаться в инструмент эксплойтов: студент не должен получать бесконечный опыт, многократно переключая статус задания «Сдано» $\leftrightarrow$ «Не начато».

### Решение
1. Опыт начисляется на основе событий `XpEvent`.
2. В таблице `XpEvent` устанавливается уникальный композитный ключ `(userId, taskId, ruleCode)`.
3. Повторная отправка того же события игнорируется на уровне транзакции БД.
4. Правила начисления очков хранятся в таблице `XpRule`, а не захардкожены в исходном коде.

### Последствия
- Невозможность накрутки очков.
- Полная аудируемость: всегда можно восстановить, за что именно был начислен каждый балл XP.
- Возможность тонкой балансировки очков старостой без изменения кода.

## ADR-007: Асинхронная синхронизация с Google Calendar через Outbox

### Контекст
Группа планирует использовать общий Google Calendar для отображения дедлайнов. Внешний сетевой вызов к Google API может завершиться ошибкой (таймаут, лимит квот, сбой сети).

### Решение
Использовать паттерн Outbox (`CalendarSyncQueue`):
- При создании или изменении дедлайна транзакция в локальной БД фиксирует изменения и кладет задачу в очередь синхронизации.
- Фоновый воркер обрабатывает очередь и обновляет событие в Google Calendar по `externalCalendarEventId`.
- Сбой внешнего сервиса никогда не приводит к откату сохранения учебного задания в системе.

### Последствия
- Мгновенный отклик интерфейса для старосты при создании задач.
- Устойчивость к сбоям внешних API.
- Исключение создания дубликатов событий в календаре.

## ADR-008: Строгий аудит источников (FACTS != PRODUCT ASSUMPTIONS)

### Контекст
В учебном процессе часто возникают слухи и противоречивые сведения. Ошибочный дедлайн или неверное требование преподавателя могут нанести реальный ущерб успеваемости студентов.

### Решение
1. Каждая информационная сущность снабжается атрибутом `provenance` (`OFFICIAL`, `TEACHER`, `HEADMAN_CONFIRMED`, `INFERRED`, `PERSONAL`).
2. При отсутствии точных данных поле остается `null` / `TBD` и отображается как «Срок не указан» (запрещено подставлять случайные правдоподобные даты).
3. При обнаружении конфликтующих данных (например, преподаватели СОВД Семенов vs Кадргулов) система поддерживает множественные записи с пометкой конфликта до официального разрешения.

### Последствия
- Высокое доверие студентов к платформе.
- Четкое понимание источника каждой даты и требования.
