## 1. Общая стратегия разработки

Разработка строится по принципу сквозных вертикальных срезов (Vertical Slices):
1. Никакие списки предметов не хардкодятся в коде — каталог курсов всегда динамический из базы данных (`CourseOffering`).
2. Геймификация (XP, уровни, достижения, лидерборд) исключена из ранних этапов — архитектура остается расширяемой, но код первых этапов сфокусирован строго на связке:  
   **User $\to$ Group $\to$ Course $\to$ Task $\to$ Deadline $\to$ Personal Progress**.
3. На каждом этапе реализуется сквозной функционал от базы данных через серверную бизнес-логику до UI с автоматическими тестами.

### Этап 2: Вертикальный срез (Vertical Slice)
**Цель:** Проверить работоспособность всей сквозной цепочки от БД до браузера на реальном сценарии.
- [ ] **Сценарий вертикального среза:**
  1. **Аутентификация:** Использование детерминированных тестовых пользователей `dev-owner` (Расул) и `dev-student`. Dev-переключатель строго изолирован условием `process.env.NODE_ENV === 'development'`.
  2. **Группа:** Вход в пространство группы `5130901/40102`.
  3. **Динамический каталог:** Получение активных курсов из БД (`CourseOffering`).
  4. **Курс и задачи:** Открытие курса (например, ОТУ), вывод списка задач с назначенными индивидуальными вариантами (`TaskVariant`) и отдельными дедлайнами (`Deadline`).
  5. **Личный прогресс (Self-Reported):** Студент меняет свой статус `NOT_STARTED` $\to$ `IN_PROGRESS` $\to$ `READY` $\to$ `SUBMITTED`. Статус персистентно сохраняется в БД.
  6. **Модель доверия (Trust Model):**
     - Обычный студент НЕ может выставить статус `ACCEPTED` (кнопка недоступна, а при прямой отправке запроса возвращается ошибка).
     - Староста (`dev-owner`) подтверждает сдачу работы $\to$ статус переходит в `ACCEPTED`, выставляется `isVerified = true` с фиксацией `verifiedById` и `verifiedAt`.
  7. **Создание задачи старостой:** Староста создает новую задачу с типом, описанием, вариантами и дедлайном (`Deadline`) $\to$ валидация Zod $\to$ проверка прав `requirePermission("manage_tasks")` $\to$ фиксация в БД $\to$ запись в доменный `AuditLog`.
  8. **Безопасность:** Обычный студент отправляет запрос на создание задачи $\to$ получает отказ `403 Forbidden` $\to$ инцидент фиксируется в `SecurityAccessLog` (доменный `AuditLog` не засоряется).
- [ ] Unit-тесты для функций проверки прав, модели доверия и расчета дедлайнов.

### Этап 3: Полноценное ядро MVP (MVP Core)
**Цель:** Довести систему до состояния боевой готовности для повседневного использования группой 40102.
- [ ] **Главная страница (Dashboard — «Что мне делать прямо сейчас?»):**
  - Блок «Фокус: что делать сейчас» с приоритетом горящих и просроченных работ;
  - Трекер прогресса семестра;
  - Сетка активных задач;
  - Лента оперативных объявлений с источниками (`SourceReference`);
  - Информативные Empty States.
- [ ] **Страницы дисциплин (Course Pages):**
  - Адаптивная структура (отображаются только непустые разделы);
  - Индикатор выполнения условий допуска к экзамену/зачету;
  - Лабораторный цикл с отображением индивидуального варианта студента;
  - Карточка преподавателей (с корректным отображением неопределенности в СОВД).
- [ ] **Страница задания (Task Page):**
  - Карточка первоисточника задания (`SourceReference`);
  - Блок вариантов с индивидуальными параметрами студента;
  - Сроки и дедлайны (жесткий/мягкий, учет времени Europe/Moscow);
  - Блок личного прогресса и подтверждения сдачи;
  - Приватные заметки студента.
- [ ] **Реестр группы и приватность (Enrollment):**
  - Список группы с реальными ФИО;
  - Генерация инвайт-токенов (`claimToken`) для связывания профиля;
  - Полная изоляция ФИО для обычных студентов (видны только никнеймы).
- [ ] **Наполнение проверенными данными (Production Seed):**
  - Все подтвержденные дисциплины семестра (ОТУ, Компиляторы, FPGA, Архитектура процессоров, СОВД, ИКГ/VR, ММФП, Образовательный форсайт, Системный анализ, САПР);
  - Все данные маркируются источниками (`Source`);
  - Демо-записи четко помечаются тегом `[DEMO]` без выдуманных дедлайнов.
