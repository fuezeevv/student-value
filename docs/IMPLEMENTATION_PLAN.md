## 1. Общая стратегия разработки

Разработка строится по принципу вертикальных срезов (Vertical Slices): вместо создания десятков изолированных фронтенд-компонентов или сотен неиспользуемых эндпоинтов, на каждом этапе реализуется сквозной функционал от базы данных через бизнес-логику до пользовательского интерфейса с обязательным тестированием.

### Этап 2: Вертикальный срез (Vertical Slice)
**Цель:** Проверить работоспособность всей сквозной цепочки от БД до браузера на реальном сценарии.
- [ ] **Сценарий среза:**
  1. Вход пользователя (авторизация с выбором роли в DEV-режиме: Студент vs Староста).
  2. Переход в группу `5130901/40102`.
  3. Просмотр тестового курса (например, «Основы теории управления»).
  4. Отображение списка задач курса.
  5. Студент нажимает кнопку смены своего статуса (`NOT_STARTED` $\to$ `IN_PROGRESS` $\to$ `READY` $\to$ `SUBMITTED`).
  6. Статус мгновенно сохраняется на сервере в `StudentTaskProgress` и восстанавливается при перезагрузке страницы (F5).
  7. Староста открывает модальное окно добавления задачи $\to$ создает новую задачу $\to$ валидация Zod $\to$ проверка прав `requirePermission("manage_tasks")` на сервере $\to$ сохранение в БД.
  8. Обычный студент пробует отправить запрос на создание задачи напрямую $\to$ получает отказ `403 Forbidden`.
- [ ] Unit-тесты для функций проверки прав и смены статуса.

### Этап 3: Полноценное ядро MVP (MVP Core)
**Цель:** Довести систему до состояния боевой готовности для повседневного использования группой 40102.
- [ ] **Главная страница («Что мне нужно делать?»):**
  - Блок самых срочных и просроченных заданий (с учетом часового пояса `Europe/Moscow`);
  - Активные задачи в работе;
  - Сводка оперативных объявлений группы;
  - Виджет общего прогресса по семестру и предметам;
  - Корректные информативные Empty States («На ближайшее время дедлайнов нет»).
- [ ] **Страницы дисциплин (Course Pages):**
  - Адаптивная структура: блоки отображаются только при наличии соответствующих данных (если нет лабораторных — блок скрыт);
  - Разделы: Лабораторные, ДЗ, Практики, Расчетные работы, Материалы, Ссылки, Требования допуска;
  - Карточка преподавателя (с поддержкой нескольких преподавателей и отметки конфликта в данных, например СОВД);
  - Индивидуальный прогресс-бар по категориям.
- [ ] **Административная панель (Admin Area):**
  - Быстрое создание и редактирование заданий старостой (минимальное число кликов);
  - Управление дедлайнами (с точным временем или датой);
  - Публикация объявлений (с закреплением и приоритетами);
  - Добавление ссылок на материалы и диски;
  - Управление участниками группы и назначение гранулярных прав (`Permissions`).
- [ ] **Приватность и реестр группы:**
  - Таблица `Enrollment` (список группы);
  - Публичное отображение только никнеймов;
  - Доступ к реальным ФИО только для администратора с правом `view_private_member_identity`.
- [ ] **Наполнение проверенными данными (Seed data):**
  - Внесение подтвержденных предметов 5 семестра (ОТУ, Компиляторы, Синтез ВС/FPGA, Архитектура процессоров, СОВД, ИКГ/VR, ММФП, САПР);
  - Маркировка подтвержденных данных тегами источников (`[OFFICIAL]`, `[TEACHER]`, `[HEADMAN_CONFIRMED]`);
  - Четкая маркировка учебных демо-данных тегом `[DEMO]` без выдуманных дедлайнов.
- [ ] **Интеграционные и E2E тесты критических путей.**

## 3. Критерии перехода между этапами
Переход к следующему этапу возможен только при выполнении следующих условий:
1. Кодовая база компилируется без ошибок (`tsc --noEmit`).
2. Линтер и тесты выполняются успешно (`npm run lint`, `npm test`).
3. Новые архитектурные решения зафиксированы в `DECISIONS.md`.
4. Реализованные сценарии проверены вручную или через автоматизированные тесты.
