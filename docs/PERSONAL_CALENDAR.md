# Персональный Google Calendar

Отдельное согласие авторизованного пользователя на `calendar.app.created`, дополнительно к обычному `openid email profile` входу. Используется тот же зарегистрированный callback `/api/auth/google/callback`, но другой AES-GCM cookie/state/nonce/PKCE flow, связанный с текущим пользователем. Полученный подписанный Google sub должен принадлежать уже связанному Google identity этого пользователя. Смена аккаунта, совпавший email или роли старосты не дают доступа к чужому календарю. Обычный login не запрашивает offline/Calendar scopes.

Refresh token хранится только как AES-256-GCM ciphertext, AAD привязывает его к конкретному пользователю и назначению. Отдельный постоянный `CALENDAR_TOKEN_KEY` находится в Vercel sensitive production environment; он отличается от server-action key и backup key. Access tokens живут только в запросе. `CRON_SECRET` защищает daily worker. Никакие credentials не сериализуются в страницы, аудит или сообщения об ошибках. При отключении приложение снимает свои напоминания, отзывает токен и удаляет локальный credential; если Google недоступен, явно просит проверить отключение в Google. Потерянный ключ требует повторного пользовательского согласия, не сброса учебной БД.

Один отдельный календарь на пользователя охватывает только его действующие Enrollment/membership. TaskAudience, публикация, действующий курс и подтверждённый source deadline проверяются тем же серверным ядром. Экспортируются будущие даты и последние 30 дней. Неизвестные сроки, черновики, чужие/неадресованные работы и личные заметки не передаются. Дата без времени — all-day event с exclusive end следующего дня; точный срок использует Moscow-aware instant. Личные READY/SUBMITTED и только trusted ACCEPTED снимают reminders, не меняя академический статус. Google-изменения не импортируются как учебная истина.

Стабильный Google event ID зависит от пользователя и Task ID, а не от изменяемого Deadline ID. Перенос обновляет то же событие. HTTP PUT / missing → INSERT / conflict → PUT допускает безопасный replay. Удалённая видимость вызывает удаление зеркального события. Сверка существования календаря выполняется перед синхронизацией. SYNCED/version/lastSyncedAt записываются лишь после ответов Google и полного прохода; частичный проход и ошибки сохраняют очередь. Academic/progress writes и requestedVersion фиксируются одной транзакцией. Lease сериализует работников; новое изменение во время прохода остаётся ожидающим. Никаких public test-auth/provider overrides нет.

Next `after()` ускоряет обработку после действий; открытие личного календаря запускает его ожидающее обновление. Постоянная очередь и leases находятся в Neon, независимо от MacBook. Один Vercel Hobby cron в день (`0 5 * * *`, UTC, точность Hobby — в пределах часа) повторяет незавершённое и выполняет сверку. Доставка не гарантированно мгновенная; текущий масштаб помещается в существующие бесплатные сервисы. Ограничение рабочего прохода и retry backoff не превращают неполный результат в успех. Новый пользовательский календарь не создаётся повторно после неоднозначного POST: восстановление по исходному calendar ID проверяет marker, либо сам пользователь явно подтверждает проверку отсутствия календаря. Замена удалённого календаря требует нового подтверждённого 404/410 от Google.

Документация, проверенная 17 октября 2026: [минимальные Calendar scopes](https://developers.google.com/workspace/calendar/api/auth), [создание отдельного календаря](https://developers.google.com/workspace/calendar/api/v3/reference/calendars/insert), [event IDs / reminders](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert), [OAuth offline flow](https://developers.google.com/identity/protocols/oauth2/web-server), [истечение testing refresh tokens](https://developers.google.com/identity/protocols/oauth2), [Next after](https://nextjs.org/docs/app/api-reference/functions/after), [ежедневный cron Hobby](https://vercel.com/docs/cron-jobs/usage-and-pricing).

## Проверки и граница реального запуска

Изолированные integration tests используют отдельную локальную PostgreSQL и подменённый wire transport только из тестов: stable event/upsert, reminder personalization, exact audience, revoke, concurrency, durable dirty versions, provider failure, ambiguous calendar creation, reconnect and disconnect. HTTP production-mode проверки доказывают CSRF/state/session/denial/cron guards без запросов к Google; они не доказывают реальный consent. Actual desktop/mobile UI проверяется отдельно на явно изолированном pending state, без фиктивного успешного Google результата.

Полный живой OAuth → secondary calendar → event readback требует отдельного согласия владельца в Google. До этого не объявлять Calendar подключённым и не создавать production test events или поддельные refresh tokens. Google Calendar API и consent/publishing configuration могут потребовать действия владельца в его Google Cloud проекте. Если приложение External/Testing, refresh tokens Calendar истекают через 7 дней; это отображено в privacy. Платный сервис или service account не используются.

Перед выпуском: 143 unit/integration tests (включая privacy и reviewer notifications), 17 browser E2E, fresh migration/catalog и production auth/health/artifact прошли. Полный Google transport проверен mock wire запросами, не реальными тестовыми событиями. Временный UI-стенд использовал только pending state, не фиктивный успешный ответ Google. Новый encrypted snapshot Neon подтверждён authenticated decrypt и pg_restore catalog; GSS negotiation отключена, TLS verify-full/system CA сохраняется. Это ручной snapshot, не независимый автоматический backup-сервис.

Финальная Vercel-сборка: 36 function traces / 160 traced files, без secrets/fixtures/browser tooling; Prisma engine включён. Смена личного этапа отдаёт приоритет очереди этого студента. Календарь с нулём событий тоже проверяется настоящим Calendar metadata response, одного успешного OAuth refresh недостаточно для SYNCED. Reviewer notification направляется только редакторам с подходящим правом и доступом к адресованной работе.
